# JWE credential encryption

`baton/jwe/v1` encrypts raw bytes to a public JWK with optional opaque
authenticated data. It does not interpret the data's application schema or verify
recipient attestations. The caller supplies the authorized recipient through its
authenticated configuration channel. Encryption does not establish sender identity.

## Configuration

Use `EncryptionConfig` with:

- `provider`: `baton/jwe/v1` (required; never inferred from key type).
- `key_id`: caller-selected recipient identifier, 1–1024 UTF-8 bytes without
  leading/trailing whitespace. This is not a thumbprint generated by the SDK.
  The serialized protected header it produces is limited separately; see the
  wire profile.
- `jwk_public_key_config.pub_key`: UTF-8 JSON public JWK, at most 16 KiB.
- `jwk_public_key_config.additional_authenticated_data`: opaque bytes, at most
  16 KiB. They are authenticated, not encrypted; do not put secrets here.

The public JWK requires `kty: "AKP"`, `alg` equal to the identifier below, and
`pub` containing the unpadded base64url X-Wing public key (1216 bytes, ML-KEM-768
followed by X25519). If present, `kid` must match `key_id`, `use` must be `enc`,
and `key_ops` must be `["encrypt"]`. Private-key members and duplicate top-level
JSON members are rejected. Other properties are ignored, never copied into JWE
headers. Unsupported algorithms and invalid keys fail before issuance.

## Wire profile

The private JOSE algorithm identifier is:

```text
https://conductorone.com/alg/hpke-xwing-hkdf-sha256-chacha20poly1305/v1
```

It selects X-Wing (`0x647a`), HKDF-SHA256 (`0x0001`) and ChaCha20-Poly1305
(`0x0003`) through the existing `filippo.io/hpke v0.4.0` primitives. This is a
private suite mapping, not HPKE-4 or HPKE-9. No new signing primitive is used.
X-Wing is hybrid post-quantum; HKDF and ChaCha20-Poly1305 are symmetric/hash
operations. The X-Wing implementation also uses its specified SHA3 combiner.

Follow integrated base-mode processing from
[HPKE for JWE draft-22, section 5](https://www.ietf.org/archive/id/draft-ietf-jose-hpke-encrypt-22.html#section-5):

- One recipient, flattened JWE JSON serialization.
- `protected` contains only `alg` and `kid`. No `enc`, `ek`, `psk_id`,
  compression, critical parameters or unprotected headers. The serialized
  protected header is at most 4096 bytes. Because JSON escaping expands some
  characters, this limit applies to the serialized header rather than to
  `key_id`, which is separately capped at 1024 bytes; a `key_id` can therefore
  serialize past the header limit and is rejected.
- `encrypted_key` is the unpadded base64url HPKE encapsulation.
- `aad` is always present, containing the unpadded base64url input context,
  including `""` for zero bytes.
- HPKE `info` is empty. HPKE AAD is ASCII(`protected + "." + aad`).
- `ciphertext` is the complete unpadded base64url HPKE ciphertext, including its
  authentication tag. JWE `iv` and `tag` are both empty strings.
- Each call uses a fresh sender context for exactly one message. Plaintext is at
  most 1 MiB and is not wrapped in an application payload.

`EncryptedData.encrypted_bytes` contains those JSON bytes directly, without an
outer base64 encoding. `provider` is `baton/jwe/v1`; `key_ids` contains exactly
the configured `key_id`; deprecated `key_id` is empty. Name, description and
schema remain carrier metadata, not authenticated JWE context.

## Issuance and compatibility

Dispatch only to connectors advertising `CAPABILITY_CREDENTIAL_ENCRYPTION_JWE`.
This capability is advertised with credential issuance support, not inferred
from generic JWK support. Older SDKs do not support this provider.

For issuance, exactly one encryption config and one plaintext value are supported.
Config fan-out fails before calling `Issue`. Unexpected provider output cardinality
returns an error without a successful encrypted response; the caller must reconcile
and revoke as appropriate, not issue a replacement credential. This SDK does not
own the caller's durable dispatch/replay lifecycle.

Existing JWK/age no-AAD behavior is unchanged. Nonempty AAD cannot be routed to
a provider that does not support it. There is no fallback between providers.

This profile pins draft-22 behavior. A different suite or wire format needs a new
explicit identifier; a library replacement preserving identical behavior does
not. Application context versioning belongs to the caller and reader.

The SDK producer alone does not establish recipient-runtime interoperability.
The consuming integration must verify stored-result authorization, native ingestion,
and ordinary read before enabling delivery.
